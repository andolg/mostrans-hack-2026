# Архитектура backend

Backend реализован в `backend/`. Целевая величина — число
посадок (успешных валидаций) для `route × date × hour`. Это не заполненность
салона и не число посадок на конкретной остановке.

## Состав

- FastAPI + SQLAlchemy: HTTP API, агрегация и работа с сохранённой ML-моделью.
- PostgreSQL: подготовленная почасовая история и кэш почасовых прогнозов.
- Docker Compose запускает контейнеры backend и PostgreSQL; frontend остаётся
  отдельным контейнером.

Модель обучается вне запуска сервиса. Backend при старте загружает её артефакты
один раз и выполняет только инференс. Текущая реализация — `SavedPredictor` в
`backend/ml/inference.py` и календарные признаки в `backend/ml/features.py`.
Backend не импортирует код из `ml_experiments/`. Снимок обученной модели хранится
в `backend/ml/artifacts/` и включается в образ; эксперименты могут меняться
независимо. Новую модель переносят в эту папку явным обновлением backend.
В контейнере работают два процесса API. Инициализация PostgreSQL выполняется
ими по очереди через advisory lock, чтобы не дублировать предрасчёт.

## Данные и граница

Подготовленный CSV `untracked/data/hourly_2025_jan_oct.csv` служит источником
истории. При первичной инициализации его загружают в БД целиком, включая строки
с нулём посадок. Последний день с известными фактическими значениями —
**2025-10-31**. Начиная с **2025-11-01** API возвращает прогноз. Граница
определяется наличием размеченных данных, а не текущей календарной датой.

Минимальная схема:

| Таблица | Ключ | Содержимое |
| --- | --- | --- |
| `actual_hourly` | `route, date, hour` | Целое `boardings ≥ 0` |
| `forecast_hourly` | `forecast_version, route, date, hour` | Целое `boardings ≥ 0` |
| `forecast_metadata` | `forecast_version` | Версия модели и признаков, дата последней истории, рассчитанный горизонт |

Две таблицы позволяют хранить факты отдельно от прогнозов и обновлять версии
модели без потери истории. Отсутствующая строка прогноза означает промах кэша;
строка со значением `0` — готовый прогноз. Отсутствующая строка истории — ошибка
полноты данных, а не нулевая посадка.

## Настройки и запуск

Backend читает `backend/settings.json`. В нём задаются путь к
подготовленной истории, путь к артефактам модели, конец размеченного периода и
длина предварительного расчёта в днях (`365` по умолчанию). Секреты подключения
к БД передаются переменными окружения. Для текущих данных стандартный горизонт
предрасчёта — **2025-11-01 … 2026-10-31** включительно.

Пример настроек (пути внутри контейнера):

```json
{
  "history_csv": "/data/hourly_2025_jan_oct.csv",
  "models_dir": "/app/backend/ml/artifacts",
  "historical_end": "2025-10-31",
  "precompute_days": 365,
  "holidays_json": "/app/backend/holidays.json"
}
```

Контейнер читает подготовленный CSV через отдельное монтирование; артефакты
модели уже находятся в образе. Сырые CSV размером около 10 ГБ для работы API
не требуются. Данные PostgreSQL хранятся в томе.

При старте backend:

1. Подключается к PostgreSQL и при необходимости создаёт таблицы.
2. Идемпотентно загружает подготовленную почасовую историю.
3. Загружает обученную модель и источники известных будущих признаков,
   в том числе календарь праздников.
4. Проверяет полноту прогнозов для всех маршрутов, часов и дней настроенного
   горизонта с учётом версии модели и признаков. Недостающие значения считает
   пакетами и записывает в БД.
5. Начинает обслуживать запросы после завершения инициализации.

Повторный запуск с теми же данными и версией не пересчитывает заполненный
горизонт. Версия прогноза — хеш файлов артефактов модели и календаря праздников.
Новая версия модели или набора признаков создаёт новую версию прогноза.
Для будущих источников данных важно использовать одинаковую подготовку
признаков при стартовом расчёте и при прогнозе по запросу.

Backend строит сетку по настройке сервиса и передаёт её в `predict_frame()`.
Готовый `submission.csv` не является источником
прогнозов приложения. `backend/holidays.json` содержит повторяющиеся даты
праздников и отдельные переносы; один и тот же календарь используется при
предрасчёте и промахах кэша. Изменения календаря нужно вносить в этот файл.
Для новых внешних признаков потребуется обновить модель.
Повторяющиеся даты задают базовый календарь для дальнейших лет; отдельные
переносы выходных нужно добавлять при появлении официального календаря.
Переносы 2026 года взяты из [постановления правительства № 1466](https://government.ru/docs/all/161028/).

## HTTP API

Основной endpoint — один интервальный запрос, например:

```http
GET /api/boardings?from=2025-11-01T00:00&to=2025-12-01T00:00&route=17&group_by=day
```

- `from` включительно, `to` исключительно; час интерпретируется в календарной
  системе датасета, без неявного преобразования часового пояса.
- `route` необязателен. Если он опущен, возвращаются отдельные ряды по всем
  поддерживаемым маршрутам.
- `group_by=hour|day|month`; дневной, месячный и годовой горизонты отображаются
  как интервалы над одной почасовой сеткой. Посадки суммируются по выбранному
  шагу, а не усредняются.
- Одночасовой интервал заменяет отдельный endpoint для `(route, date, hour)`.
- Ответ содержит границы интервала, маршрут, значение и источник `actual` или
  `forecast`; для прогноза также возвращаются дата исходной истории и версия.
  Если агрегат пересекает границу фактов и прогнозов, его части различаются по
  источнику, чтобы сумма не выглядела целиком фактической.

Для прогноза backend читает готовые строки из БД. Если часть запрошенной
сетки отсутствует, он пакетно вызывает загруженную модель для недостающих
`route × date × hour`, сохраняет результат и затем агрегирует полный интервал.
Это позволяет запрашивать даты после предварительно рассчитанного горизонта как
исследовательский сценарий. Готовые дневные и месячные значения суммируются в
PostgreSQL. Исторические пропуски моделью не заполняются.

`GET /api/metadata` отдаёт поддерживаемые маршруты,
последнюю дату истории, конец предрассчитанного горизонта и активную версию
прогноза. Frontend имеет собственную настройку видимого диапазона и возможности
выходить за горизонт, но сверяет фактические границы с этими метаданными.
`GET /health` проверяет готовность сервиса. Позже экспорт CSV может
использовать те же параметры интервального запроса.

## Область применимости и проверка

Текущая модель проверялась на прогнозе следующих двух месяцев; годовой горизонт
и запросы за пределами предрасчёта являются исследовательскими прогнозами.
Интервал после 2025-10-31 остаётся прогнозом даже после наступления этих дат,
пока не поступят фактические валидации. Данные не дают достоверной детализации
по остановкам: `place_id` обозначает площадку/депо.

Измеренные 400 RPS и p95 1,42 мс относятся только к ML-инференсу без HTTP и БД.
Замер полного API с 2 vCPU и 2 ГБ RAM приведён в корневом README: при заданных
400 RPS в двух прогонах достигнуто 373–392 RPS, p95 112–239 мс для
кэшированных часовых запросов.
Подробности о данных и существующих замерах:
[датасет](../data/README.md), [ML-пайплайн](../ml/README.md),
[результаты](../../ml_experiments/RESULTS.md).
